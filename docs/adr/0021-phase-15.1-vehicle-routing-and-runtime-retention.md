# ADR 0021: Bind simulator state to vehicle identity and bound runtime diagnostics

- Status: Accepted
- Date: 2026-09-09

## Context

Phase 15 observed HTTP 500 responses when a session identity used a vehicle other
than the simulator's single process-global vehicle. The same qualification also
found V8 old-space exhaustion at the unchanged 160 MiB limit. Runtime cache size
and conversation history were already bounded, but every cached runtime retained
large run, trace, and event identifier sets.
The first formal 30-minute soak then proved those bounds were insufficient:
old-space still grew until one API restart. A four-profile isolation run and
retention audit localized the remaining growth to Tool execution. Each runtime's
`ReliableToolExecutor` permanently retained completed process-local execution
records and idempotency promises even though PostgreSQL was already authoritative.

## Decision

The API passes the authenticated session vehicle identity into the production
runtime and `SimulatorClient`. The client sends it as the validated
`x-driveguard-vehicle-id` boundary header. The simulator service routes every
state read and transition through a bounded `VehicleSimulatorFleet`, with one
serialized simulator instance per vehicle. Reservation idempotency is scoped by
vehicle. Sessions intentionally naming the same vehicle share that state.

Runtime diagnostic identifier sets are bounded to the smallest limits that
preserve duplicate and cancellation diagnostics: 256 run identifiers, 256 trace
identifiers, and 2,048 emitted event identifiers per runtime. Public lifecycle
interfaces and the Policy -> Confirmation -> Reliable Executor side-effect path
are unchanged. Resource gauges expose aggregate retained counts for qualification.

When a durable execution coordinator is present, completed process-local
execution records and idempotency entries are released only after the durable
coordinator has finalized the authoritative result. The non-durable executor
keeps its original in-memory replay behavior. No entry is evicted while an owner
is running, and PostgreSQL continues to enforce replay, conflict, fencing, audit,
and restart behavior.

Context source reads retry once only when domain validation reports a future
timestamp. The retry rereads every source and retains the original fail-closed
`CONTEXT_INVALID` outcome for any repeated future timestamp or any other
validation failure; it does not relax timestamp validation or reinterpret an
invalid context as a successful action.

## Consequences

- Session state remains keyed by `sessionId`; simulator state is keyed by
  `vehicleId`; confirmation and execution continue to bind all three identity
  dimensions.
- No LLM actuator capability is added and no simulator mutation bypass is added.
- A simulator process accepts at most 1,000 distinct vehicle identities and
  fails closed for additional identities instead of evicting live state.
- The heap limit remains 160 MiB. The 30-minute qualification soak, not this
  design decision alone, determines whether the retained-object fix is adequate.
- The retry is not a Stage Gate pass: the third formal soak still recorded two
  repeated `CONTEXT_INVALID` HTTP 500 responses, so further root-cause work is
  required before another qualifying soak.
